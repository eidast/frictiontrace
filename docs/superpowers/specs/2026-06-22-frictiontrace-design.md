# FrictionTrace — Design Document

**Date:** 2026-06-22
**Status:** Approved (brainstorming complete)
**Mode:** Read this spec top-to-bottom to understand the system, then jump to [Phasing](#phasing--milestones) for what to build first.

---

## TL;DR

FrictionTrace is a **digital experience monitoring** tool focused on **user friction** in e-commerce sites. It runs real browsers against a target site, captures rich signals, and produces a report covering four perspectives: end client (what they felt), developer (what to fix), site owner (impact in $ and risk), and broader impacts (compliance, vendor lock-in, etc.).

**Business shape:** one-shot audits first, productized SaaS later. **Engine is open source**; the LLM narrative layer and hosted dashboard are the paid service.

**Stack:** Node.js, Playwright, SQLite, open core (MIT/Apache 2.0).

## Components

Six isolated units. Each does one thing, exposes a small interface, depends on nothing further down the pipeline.

| # | Component | Responsibility | Interface | Depends on |
|---|---|---|---|---|
| 1 | **Trigger** (CLI + API) | Accept target URL, optional journey override, flags. Return `runId` + dashboard URL immediately. | `submitRun(input) → { runId, statusUrl }` | Orchestrator |
| 2 | **Orchestrator** | Validate input, pick journey (override or default), create `runs` record, enqueue work. | `enqueue(input) → runId` | Worker queue, SQLite |
| 3 | **Worker** (Playwright runner) | Launch Chromium, configure HAR/MHTML/trace/video, execute each journey step, capture signals + screenshots, commit artifacts. | `processRun(runId) → { status, signalCount }` | Playwright, CDP, SQLite, filesystem |
| 4 | **Analyzer** | Read signals, apply rules, emit issues (kind, severity, evidence) and facts (key, value, source signals). Pure code, no LLM. | `analyze(runId) → { facts, issues, scores }` | SQLite only |
| 5 | **Narrative layer** (LLM) | Receive facts + site context, produce developer insights and impacts section. Each insight references `fact_ids` (anti-hallucination). Failure-safe: if LLM down, report ships without this layer. | `narrate(facts) → { developerInsights, impacts }` | LLM provider |
| 6 | **Renderer** | Assemble report doc, serve web dashboard by `runId`, generate PDF on demand. Stateless given a report doc. | `render(report) → { url, pdfPath }` | Report doc, template engine |

**Isolation rules:**
- Worker doesn't know about issues — only writes signals.
- Analyzer doesn't touch the browser — only reads SQLite.
- LLM is called only after facts exist. If it fails, the report ships without it.
- Renderer is stateless: given a report doc, it produces web + PDF.
- Everything is testable with fixtures: analyzer tested against pre-populated SQLite.

## Signal taxonomy (10 categories)

The Worker writes to a single `signals` table. Each row has `category`, `type`, `payload_json`, `captured_at`, `step_id`.

| # | Category | What | Used for |
|---|---|---|---|
| 1 | Web Vitals + perf | LCP, INP/FID, CLS, TTFB, FCP, TTI, long tasks (>50ms), JS heap size, fps | "Page feels slow" |
| 2 | Console | `console.log/info/warn/error/debug` + `pageerror` | Programming errors, deprecation warnings |
| 3 | Network | URL, method, status, type, sizes (transfer/encoded/decoded), per-phase timing (DNS/TCP/TLS/TTFB/download), cache, redirects | Latency, heavy assets, failures |
| 4 | JS exceptions | Message, stack, file:line:col, frequency, URL context | "Errors from bad programming" |
| 5 | DOM / UX | Broken images (`naturalWidth=0`), forms without labels, failed iframes, broken autofocus, scroll jank | Visible user friction |
| 6 | Page lifecycle | DOMContentLoaded, load, networkidle, redirect count, final URL | When the site is "ready" |
| 7 | Storage & consent | Cookie count/size, localStorage writes, CMP/banner presence, third-party cookies | Legal/privacy risk |
| 8 | Security | Mixed content, form action on HTTP, password fields without safe autocomplete, deprecated APIs | Security risk |
| 9 | Third-party inventory | Per domain: type (analytics/ads/payments/chat/CDN/tag-manager/marketing), total weight, latency, failures | "Latency from third-party calls" |
| 10 | Journey evidence | Screenshots per step, time per step, success/failure per step, signals filtered by `step_id` | Reproducibility, evidence for owner and dev |

### SQLite schema

```sql
CREATE TABLE runs (
  id TEXT PRIMARY KEY,
  target_url TEXT NOT NULL,
  status TEXT NOT NULL,           -- queued | captured | analyzed | narrated | done | error
  started_at INTEGER, finished_at INTEGER,
  config_json TEXT,
  journey_id TEXT,
  warnings_json TEXT DEFAULT '[]'
);

CREATE TABLE steps (
  id TEXT PRIMARY KEY,
  run_id TEXT REFERENCES runs(id),
  name TEXT, status TEXT,         -- ok | failed | timeout | skipped
  started_at INTEGER, finished_at INTEGER,
  screenshot_path TEXT
);

CREATE TABLE signals (
  id TEXT PRIMARY KEY,
  run_id TEXT REFERENCES runs(id),
  step_id TEXT REFERENCES steps(id),
  category TEXT,                  -- 1..10 above
  type TEXT,                      -- sub-type within category
  payload_json TEXT,              -- category-specific
  captured_at INTEGER
);

CREATE TABLE screenshots (
  id TEXT PRIMARY KEY,
  run_id TEXT REFERENCES runs(id),
  step_id TEXT,
  path TEXT,                      -- filesystem path
  kind TEXT,                      -- viewport | above_fold | full_page
  width INTEGER, height INTEGER
);

CREATE TABLE issues (
  id TEXT PRIMARY KEY,
  run_id TEXT REFERENCES runs(id),
  kind TEXT,                      -- catalog, see Signal→Issue table
  severity TEXT,                  -- low | med | high | critical
  summary TEXT,
  evidence_json TEXT              -- array of signal_ids
);

CREATE TABLE facts (
  id TEXT PRIMARY KEY,
  run_id TEXT REFERENCES runs(id),
  key TEXT,
  value_json TEXT,
  source_signal_ids_json TEXT
);

CREATE TABLE report_docs (
  id TEXT PRIMARY KEY,
  run_id TEXT REFERENCES runs(id),
  executive_json TEXT,            -- template-rendered
  insights_json TEXT,             -- LLM-rendered (or null)
  rendered_at INTEGER
);

CREATE TABLE journeys (
  id TEXT PRIMARY KEY,
  name TEXT,
  config_json TEXT                -- see Journey config schema
);
```

## Signal → Issue → Perspective mapping

The Analyzer is pure code. It transforms signals into issues (kind, severity, evidence) and facts (key, value, source). Issues and facts are then grouped by perspective in the report.

| Signal | Issue kind | Appears in |
|---|---|---|
| `pageerror` (repeated) | `js_error` (with stack) | Cliente, Developer, Impactos |
| 3rd-party > 1.5s on main thread | `third_party_blocking` | Cliente, Developer, Impactos |
| LCP > 2.5s | `slow_lcp` | Cliente, Dueño, Developer |
| INP > 200ms | `slow_interaction` | Cliente, Developer |
| CLS > 0.1 | `layout_shift` | Cliente, Developer |
| Image broken | `broken_image` | Cliente, Developer |
| Mixed content | `mixed_content` | Developer, Impactos |
| No consent banner + cookies set | `consent_missing` | Dueño, Impactos |
| Failed request to checkout API | `checkout_broken` | Cliente, Dueño, Developer |
| Long task > 100ms | `jank` | Cliente, Developer |
| Script > 500KB | `heavy_script` | Developer |
| Deprecated API usage | `deprecation` | Developer, Impactos |

**Issue schema (closed catalog):**
- `kind`: enum (the table above + future additions)
- `severity`: `low` | `med` | `high` | `critical`
- `summary`: short human description
- `evidence`: array of `signal_id`s (this is what makes the LLM "grounded" — it can only reference these)

**Facts (open-ended key-value):**
- Examples: `home.lcp_ms = 3200`, `cart.third_party_count = 7`, `home.consent_banner_present = false`
- Facts feed both the templates (executive) and the LLM (narrative).

### The 4 perspectives in the report

**1. Cliente final (end client)** — human language, no jargon.
> "On the 'add to cart' step the browser froze for ~3 seconds. You probably felt the page was broken. The cause was an external analytics script."

**2. Developer** — technical, actionable, with evidence.
> "Tag manager loads Segment script (320KB) blocking main thread 2.1s before DOMContentLoaded. Suggestion: defer or async; move to a web worker. Evidence: signal_id=ab12, signal_id=cd34."

**3. Dueño del sitio (site owner)** — executive, dollar impact.
> "3 critical issues affect the checkout funnel. Estimate: 6–9% of carts lost. With your AOV of $X, that's $Y/month recoverable."

**4. Impactos / riesgos (impacts)** — what could go wrong.
> "HIGH risk: payments vendor fails 1.4% of the time historically with no fallback. If it fails during peak hours, you lose 100% of checkout. Recommendation: implement fallback."

## Replay artifacts (all generated by default)

| Artifact | What | Who uses it | How to open |
|---|---|---|---|
| `run.har` | All requests with timing, headers, sizes, status | Developer | Chrome DevTools → Network → Import HAR |
| `run.mhtml` | Full navigable page as a single file | Owner, Developer | Double-click in Chrome |
| `trace.zip` | Playwright trace: clicks, network, console, screenshots in time | Developer | `trace.playwright.dev` |
| `step-*.png` | 3 screenshots per step (viewport, above-the-fold, full-page) | All | Web viewer, embedded in PDF |
| `run.webm` | Continuous video of the whole session | Owner (visual issues) | Standard player |

**HAR generation strategy:** reconstructed from our `signals` table (we already have all data: URL, method, status, sizes, per-phase timing). No extra CDP plumbing needed. Function: `signalsToHar(runId) → HAR JSON`.

**MHTML generation strategy:** Chrome DevTools Protocol `Page.captureSnapshot` returns an MHTML string. Captured at the end of the journey.

## Data flow (one run, end to end)

```
1. Trigger
   · Input: target URL, optional journey override, flags
   · Output: runId immediately, statusUrl (dashboard)
   · Fails: invalid URL → 400

2. Orchestrator
   · Creates runs record (status=queued)
   · Resolves journey: override or default
   · Validates journey schema → fail=error
   · Enqueues work for Worker
   · Fails: invalid journey → run=error

3. Worker (Playwright + CDP)
   · Launches Chromium, configures HAR/MHTML/trace/video
   · For each step:
       - navigate, interact, wait
       - capture 3 screenshots
       - capture signals (10 categories)
       - if step fails: log + mark step=failed, continue
   · At end: closes browser, commits artifacts + signals
   · Marks run.status = captured
   · Fails: browser can't start → run=error, no retry

4. Analyzer
   · Reads signals, runs rules (pure code)
   · Writes issues + facts
   · Marks run.status = analyzed
   · Fails: SQLite corrupt → run=error, no retry

5. Narrative layer (LLM)
   · Receives facts + site context
   · Produces developer insights + impacts section
   · Each insight cites fact_ids (no invention)
   · Marks run.status = narrated
   · If LLM fails: marks run.status = analyzed_with_warnings, insights=null
   · Never blocks the report

6. Template layer (deterministic)
   · Reads facts + issues, applies templates
   · Produces executive summary, scores, top 5 issues
   · Always runs

7. Renderer
   · Assembles report doc (executive + issues + insights)
   · Persists in report_docs
   · Serves dashboard at /runs/{runId}
   · Generates PDF on demand (Playwright print API)
   · Marks run.status = done
   · Fails: PDF fails → dashboard keeps working
```

**Run states:** `queued → captured → analyzed → narrated → done`. Any state can transition to `error` with a `warnings_json` array describing what went wrong.

## Error handling principles

1. **The engine never aborts a run for an expected error.** Slow site, missing selector, third-party down — all are signals, not exceptions.
2. **Engine-level errors do break the run.** Worker can't start, SQLite corrupt, disk full → run=error, no automatic retry.
3. **The report is always delivered** (dashboard accessible), even if sections are missing. The owner sees "this was measurable, this wasn't".
4. **Failures are observable.** Every run has `status` and `warnings[]`. The dashboard surfaces warnings prominently.
5. **LLM is optional.** If the narrative layer fails, the report ships with `insights: []` and an "AI analysis unavailable" banner. The deterministic executive section (which is what the owner looks at first) is never affected.

**Specific failure modes and behavior:**

| Failure | Behavior |
|---|---|
| Site doesn't respond | Step timeout → step=timeout, continue |
| Selector doesn't exist | Step fail → log + screenshot, continue |
| 3rd-party blocks | Captured as signal, not blocking |
| LLM API down | Report delivered without LLM section, marked "AI analysis unavailable" |
| Browser crash | Worker retries once with fresh browser |
| PDF render fails | Dashboard stays accessible, PDF regenerable on demand |
| Journey incomplete | Report delivered with "steps not completed" + explanation |

**What we explicitly do NOT do:**
- We don't retry failed steps. Friction **is** the report. A step failure is a finding, not something to retry.
- We don't use Firefox or Webkit. Playwright supports them, but the HAR/MHTML/trace ecosystem is best in Chromium. Single browser keeps the test fixture simple.

## Journey configuration

The journey is a **declarative YAML file** executed by the Worker. It's interpreted, not scripted.

### Schema

```yaml
name: default-ecommerce-v1
version: 1
target:
  baseUrl: ${URL}            # substituted at runtime
  country: AR
  currency: ARS

settings:
  viewport: { width: 1366, height: 768 }
  userAgent: desktop          # desktop | mobile
  locale: es-AR
  timezone: America/Argentina/Buenos_Aires
  throttle: none              # none | slow-3g | slow-4g
  cookies: []                 # optional, e.g. to bypass consent

artifacts:
  har: true
  mhtml: true
  trace: true
  video: true
  screenshots: { viewport: true, fullPage: true }

steps:
  - name: home
    kind: navigate
    url: /
    waitFor: domcontentloaded   # networkidle | load | selector
    timeoutMs: 10000
    assertions: [console_no_errors, status_2xx]

  - name: search
    kind: interact
    actions:
      - findSelector: input[name="q"], input[type="search"]
        fallback: [input[placeholder*="buscar" i]]
        onError: skip_step       # fail_step | skip_step | continue
        type: "zapatillas"
        pressEnter: true
    waitFor: networkidle
    timeoutMs: 8000

  - name: pick_product
    kind: extract_and_click
    selector: a.product-card:first-of-type, [data-testid="product"] a:first-of-type
    fallback: [a[href*="/producto/"]:first-of-type]
    waitFor: domcontentloaded

  - name: product_detail
    kind: interact
    actions:
      - scroll: { to: bottom, smooth: true }
    waitFor: networkidle

  - name: add_to_cart
    kind: interact
    actions:
      - findSelector: button[data-testid="add-to-cart"], button:has-text("Agregar al carrito")
        optional: true
        action: click
        afterMs: 1500

  - name: cart
    kind: navigate
    url: /cart
    waitFor: domcontentloaded

  - name: checkout
    kind: navigate
    url: /checkout
    waitFor: networkidle
    # stop: no llenamos forms
```

### Three authoring modes (all in MVP)

| Mode | UX | Audience | Cost |
|---|---|---|---|
| **1. YAML + `ft validate`** | Hand-edit the YAML, run `ft validate` to dry-run it | FrictionTrace team (one-shot), advanced users | Lowest: pure code + CLI |
| **2. UI in dashboard** | Drag steps, paste selectors, dry-run with one click. UI generates the YAML underneath. | Devs at e-commerce (SaaS) | Medium: frontend work |
| **3. Record & replay** | Developer opens an instrumented browser, interacts manually, system generates the YAML from the trace. | Non-technical configurators, complex custom sites | Highest: codegen + editing UI |

All three produce the **same YAML artifact**. The Worker is mode-agnostic.

## Testing strategy (4 layers)

| Layer | Covers | How | When |
|---|---|---|---|
| **1. Unit** | Pure functions: signal analysis, signal→issue mapping, HAR reconstruction, executive templates | Vitest. SQLite pre-populated with fixture signals. Asserts on issues/facts emitted. | Every commit (CI) |
| **2. Contract** | Journey YAML schema validation: rejects malformed configs | Zod or JSON Schema. Edge cases: steps without selector, negative timeouts, unknown actions. | Every commit (CI) |
| **3. Integration** | Worker runs a real journey against a static fixture site | Playwright Test. Asserts expected signals present, screenshots non-empty, HAR well-formed. | Every PR (CI) |
| **4. Golden** | End-to-end run against 2-3 reference sites (our demo shop + 1 real shop, stable). Snapshot of issues and facts. | Snapshot comparison. If it changes, manual review. Detects analyzer and journey-runner regressions. | Nightly + pre-release |

### The fixture site (planted bugs)

A static mini e-commerce we host, with bugs planted on purpose:
- One broken image (404)
- One script that emits `console.error` every 2 seconds
- One fake third-party endpoint with 2.5s delay
- Mixed content (an `http://` asset on an `https://` page)
- A layout shift from a late-loading banner
- A slow LCP (hero image > 2.5s)

Integration test runs a journey against this site and asserts that **all expected issues are detected**. If one stops being detected, the test fails and we fix the analyzer.

### What we don't test (yet)

- **LLM output** is non-deterministic. We test that the prompt produces parseable JSON and every insight cites a valid `fact_id`.
- **Dashboard visuals** get a Playwright smoke test (loads, doesn't crash), not pixel-perfect.
- **PDF** is snapshotted by hash. Layout changes require manual review.

## Open core boundary

### Open source (public repo, MIT or Apache 2.0)
- Orchestrator (CLI + enqueue)
- Worker (Playwright runner + signal capture)
- Analyzer (signal → issues + facts)
- HAR / MHTML / trace generators
- Template layer (deterministic executive summary)
- Journey schema + validator
- CLI commands: `ft run`, `ft validate`, `ft replay`
- Authoring modes 1 (YAML) and 3 (record & replay)
- Local HTML renderer (static report file, no dashboard)

### Closed / service (SaaS, code not public)
- Narrative layer (LLM)
- SaaS Renderer (web dashboard interactive per runId)
- PDF generator (polished version)
- Authoring mode 2 (UI in dashboard)
- Hosting, billing, auth, multi-tenant
- Historical reports, comparisons, alerts

### Library (open) consumed by SaaS (closed)
- The open core is consumable as a library. The SaaS doesn't duplicate the engine; it wraps it.

### What the owner gets for free (open core)
```bash
$ npx frictiontrace run https://mi-tienda.com
$ open report.html     # templated report, no LLM
```

### What the owner pays for (SaaS)
- Developer insights narrated by LLM with evidence
- "Impacts and risks" section
- Interactive web dashboard with drill-down
- Downloadable PDF
- Historical runs, comparisons, alerts
- UI to customize journey without touching YAML

### Why this line works
- The open core **is useful by itself** (templated report is valuable, free, fast).
- The SaaS **doesn't compete** with the open core; it complements it. No SaaS user feels "I could have done this for free" — the LLM is what justifies the price.
- The dev at the e-commerce can fork the repo, add their own analyzer rules, and contribute back.

## Phasing / Milestones

This design is large. It is **not** a single implementation plan. The MVP that proves the concept is **M0**; the rest is a roadmap.

### M0 — Open core MVP (proof of concept, ~1-2 weeks)
- Worker + 10 signal categories
- Analyzer with ~5 issue kinds (the high-value ones: js_error, third_party_blocking, slow_lcp, mixed_content, checkout_broken)
- Executive template (top issues + scores)
- HAR + MHTML generation
- Local HTML renderer (CLI: `ft run <url>` → `report.html`)
- Mode 1 (YAML) authoring
- Planted-bug fixture site + integration test
- **No LLM, no dashboard, no PDF, no auth, no UI**

This is enough to:
- Run a real audit end-to-end
- Show a real report to a potential customer
- Validate that the signal capture + analysis works

### M1 — Add LLM narrative + service mode
- Narrative layer (OpenAI / Anthropic)
- Hosted web dashboard per runId (single user, no auth yet, or single-tenant)
- PDF generator
- LLM failure handling
- **No multi-tenant, no billing**

### M2 — Multi-tenant SaaS
- Auth, billing
- Historical runs, comparisons
- Alerts
- Mode 2 (UI authoring) in dashboard

### M3 — Record & replay + hardening
- Authoring mode 3
- Golden tests on 2-3 reference sites
- Nightly CI
- Documentation site

### M4 — Polish and growth
- Per-step video highlights
- More journey templates (fashion, marketplace, B2B, etc.)
- Public roadmap / open source community building

## Open questions / future work

These are deliberately out of scope for M0–M4 but worth tracking:

1. **Consent for crawling.** Some sites prohibit automated access. M0 should support a `robots.txt`-aware mode and a `dryRun` flag. Future: a whitelist of "audit-only" e-commerce vendors.
2. **Authentication on the target site.** Some audits need to log in (e.g., to test account pages). M0 doesn't support this. M2+ will need a credentials vault + a journey config that can use them.
3. **Mobile journeys.** M0 is desktop-only. Mobile (with `userAgent: mobile` and proper viewport) is an extension of the existing config.
4. **Multi-page journeys** beyond the default 7. M0 default is home → search → product → cart → checkout. Customers can override.
5. **Localization of the report.** The report's natural language is configurable. M0 ships English + Spanish. Detection of site locale is post-M0.
6. **Anomaly scoring over time.** Comparing runs across time, detecting regressions. M2+ requires storing historical data.
7. **Privacy of captured data.** MHTML and HAR contain everything, including cookies and tokens. M0 should warn before saving, and the SaaS must scrub PII before storing.

## Glossary

- **Friction:** any user-facing or developer-facing issue that degrades the experience — slow load, broken layout, JS error, missing CTA, third-party vendor block, etc.
- **Run:** a single execution of a journey against a target URL. Has a unique `runId`, produces one report.
- **Journey:** the sequence of steps the Worker executes (configured via YAML).
- **Step:** a single navigation or interaction in the journey (e.g., "go to /search", "click first product").
- **Signal:** a raw captured data point in one of the 10 categories.
- **Issue:** a finding emitted by the Analyzer, grounded in evidence (signal_ids).
- **Fact:** a structured key-value derived from signals, used by templates and the LLM.
- **Perspective:** one of the 4 sections of the report (Cliente, Developer, Dueño, Impactos).
- **Artifact:** a replay/evidence file (HAR, MHTML, trace, screenshots, video).
